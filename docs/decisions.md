| D-000 | 2026-09-27 | Stack: Python 3.13 + uv, Pydantic v2, YAML layered config, FastAPI mocks (one process per service), httpx, SQLite, in-house LLM client (`openai_compat` + `anthropic` adapters) with record/replay, Typer + Rich CLI, pytest, in-house eval runner. The `refund_issuance` action (DRAFT, optional AUTO threshold) applies only to damaged / wrong / never-arrived remedies. Return replies must not promise a refund date or claim a refund was issued. | User decision. |
| D-003 | 2026-09-27 | Default model for all LLM steps: **Qwen 3.8 27B via LM Studio** (OpenAI-compatible API). | D-004 | 2026-09-27 | Email files are **JSON**, one file per email; format documented in `docs/email-format.md` (intake milestone). | User decision. |
| D-005 | 2026-09-27 | Git remote: `https://github.com/SureshKhemka/custsupportemailrouter`. | User decision. |
| D-006 | 2026-09-27 | Default operating mode is **`shadow`** (process fully, send nothing). Eval and demo overlays switch to `live` (writing to the mock outbox). | Safest default; "humans own risk". |
| D-007 | 2026-09-27 | Beyond FR-19: `CLOSE` (no reply) is allowed only for `spam_or_auto`; legal/abuse must be exactly `ROUTE_NO_DRAFT`; the routing matrix must cover exactly the taxonomy intents. Enforced in code. | Prevents silently dropping a real customer email via config. |
| D-008 | 2026-09-27 | Config files may not contain secret-looking values (e.g. `sk-...`); `api_key_env` must be an environment-variable **name**. Validation fails otherwise. | CF-3 defence against pasting a key into YAML. |
| D-009 | 2026-09-27 | Repeat-contact escalation defaults to the **2nd contact** on the same issue within 14 days. | FR-16 "repeat contact"; configurable. |
| D-010 | 2026-09-27 | Each mock runs as **its own process and port** (`mocks up` supervises them). Services only read their own seed files; they do not call each other. | Faithful to "separate services over a network" (section 4); any one can be replaced by config. |
| D-011 | 2026-09-27 | The order service reports **raw fulfilment status** only. "Delayed" and "lost" are not statuses: router code derives them from `promised_delivery_date` and the last tracking event (PO-4). Seed "delayed"/"lost" orders are `in_transit` with the right dates. | Keeps policy decisions in router code (FR-23). |
| D-012 | 2026-09-27 | Mock action services validate only **facts they own** (order exists, line belongs to order, quantity left, stock, refund not exceeding amount paid). They do **not** enforce policy (return window, non-returnable categories); the router does. | Policy lives in one place. The mocks still act as a last-line guard against over-refunding. |
| D-013 | 2026-09-27 | Creating a return in the returns service does **not** change the order's status in the order service (no cross-service propagation in mocks). The router reads return state from the returns service. | Simplicity; mirrors eventually consistent real systems. |
| D-014 | 2026-09-27 | Idempotency: same key + same payload returns the original result (HTTP 200, `Idempotent-Replayed: true`); same key + different payload returns 409; validation failures are not remembered. The outbox is idempotent too, so a replayed case cannot send two replies. | FR-24, NF-5, HG-4. |
| D-015 | 2026-09-27 | Fault kinds: `error` (503, nothing done), `timeout` (hang, nothing done), `timeout_after_commit` (action done, caller times out). Random faults use a seeded RNG, so runs are repeatable. | MS-9, EV-11. `timeout_after_commit` is the case that breaks naive retries. |
| D-016 | 2026-09-27 | Mock state and call logs persist in `var/mocks/`. Persisted state is discarded (reseeded) if the seed files change or the pinned "now" differs. | NF-5 (reprocessing is safe across mock restarts) without stale data. |
| D-017 | 2026-09-27 | Seed return and refund amounts follow PO-2: ordinary returns refund item price only (no shipping). The dataset's "recent orders" scenarios assume a candidate window of about 60 days. The window becomes config in the identity milestone. | Keeps seed consistent with policy for the DS-5 check. |
| D-018 | 2026-09-27 | Ambiguous **handling choices are configuration** (`config/handling.yaml`), with safe defaults and per-intent overrides: escalation of an AUTO case → **DRAFT** (or ROUTE); multi-intent actions while the case waits for a human → **hold** (or run, only for non-monetary return/cancel); prompt injection → **escalate** (or flag only); unverified sender → **template reply** (or route); ambiguous order → **clarify** (or route); candidate-order window **60 days**. FR-19 invariants still enforced in code; escalation can never produce AUTO. | User: "Make it a configuration, we can change it based upon system performance or case type." |
| D-019 | 2026-09-27 | Order service gets an idempotent `POST /orders/{id}/cancel` (refuses once shipped). Refunds for prepaid cancellations are handled by the platform, like return refunds (D-002). | FR-18 allows AUTO cancel before shipping; no mock could perform it. |
| D-020 | 2026-09-27 | Deterministic policy functions (`router/decide/policy.py`) and case routing (`router/decide/routing.py`) were built in M3, because the DS-5 label check needs them. M4 extends their tests. Labels are written by hand and checked against this code, so each cross-checks the other. | DS-5 requires an automatic consistency check. |
| D-021 | 2026-09-27 | Window counting: calendar days in `app.timezone`; the last day counts (return day 30 of 30 is eligible; damage day 7 of 7 is in time). "Lost" = at least 7.0 elapsed days since the last tracking event. "Late" = the promised date is before today. Photo required only when unit price is **strictly above** the threshold. | PO-1, PO-3, PO-4 boundaries needed an exact rule. |
| D-022 | 2026-09-27 | Refund for damaged/wrong/never-arrived = item price × quantity affected + the order's shipping fee once. Remedy is a replacement only if every affected item is in stock, otherwise a refund. | PO-2, PO-3. |
| D-023 | 2026-09-27 | Unsupported-language emails go to a human (ROUTE, no auto draft). The queue follows the strictest intent (e.g. a German legal threat goes to legal). Hinglish/code-mixed counts as Hindi. | FR-5 with D-001. |
| D-024 | 2026-09-27 | An unverified sender on an order-bound request gets the identity template reply unless the case needs a human anyway (ROUTE or stricter, e.g. legal); then it is routed and no order data goes out. A registered customer with no matching order goes to a human. | FR-10, FR-8. |
| D-025 | 2026-09-27 | Queue for a human case = strictest-ranked queue among its intents: legal > abuse > billing > general. Legal is flagged priority. | FR-20, FR-35. |
| D-026 | 2026-09-27 | Dataset records are processed in **isolated groups** (fresh router state and mock reset per group; threads and duplicates share a group), so independent emails about the same seed order never affect each other. Records carry `@now`-relative dates against `dataset.yaml: reference_now`. | Lets the dataset reuse seed scenarios without cross-contamination. |
| D-027 | 2026-09-27 | Several requests of the same intent for different orders ("where are A and B?") are separate intents with different `order_id`s. | FR-12 "one thing the customer wants". |
| D-028 | 2026-09-27 | DS-7 ratings are drafted by Claude and marked `rated_by: claude-draft` until a human reviews them. The judge-agreement report (EV-8) must show how many are still drafts. | Human judgement cannot be simulated honestly; the user reviews. |
| D-029 | 2026-09-27 | Case id = hash of the thread's first message id. Action idempotency key = `case:action:order:digest(lines, amount)`. Retries and replays reuse the key. A genuinely different action in the same case (other lines or amount) gets a new key. Nothing depends on time or randomness. | FR-24, NF-5: reprocessing from an empty router DB still cannot repeat an action. |
| D-030 | 2026-09-27 | Operating modes: `shadow` = decide and record, but send nothing and run no action. `draft_only` = AUTO becomes DRAFT and no action runs automatically. A case uses the most cautious mode among its intents. | FR-22: the modes may only make outcomes more cautious. |
| D-031 | 2026-09-27 | SLA = tightest SLA among the case's intents; "approaching" once `sla.approaching_fraction` (75%) has elapsed. Spam and closed cases have no SLA. | FR-37. |
| D-032 | 2026-09-27 | Order resolution: ids mentioned in the email → else the only recent order → else a unique match between item words and order lines → else ambiguous (ask). Order-id patterns: `ORD-n`, `ORD n`, `#n`, `order n`, `order no./number n`. | FR-8, FR-11: never guess between several orders. |
| D-033 | 2026-09-27 | Customer-based escalation signals (VIP, high value, repeat contact) apply only when ownership is verified. Tone signals need the configured minimum LLM confidence. | FR-16 without letting someone borrow another customer's status. |
| D-034 | 2026-09-27 | Outbound gate is deterministic and only blocks, never rewrites. Dates are checked by meaning ("delivered on X" must equal the delivery date; "N days ago" must match). Amounts must come from backend records or policy decisions. Action claims ("has been refunded / cancelled", "we've created a return") need a succeeded action or matching backend state. Negated promises ("we can't guarantee") are allowed. Reply language is detected with `lingua` (customer emails, including code-mixed, are classified by the LLM). | FR-31. Checked against DS-6 (all 22 correct, HG-5) and against the DS-7 replies rated correct (none wrongly blocked). |
| D-035 | 2026-09-27 | Pipeline order is **intake → understand → identify → decide → act → reply → gate**. Identity runs after understanding because it needs to know whether any intent is about an order (only then is an order inferred from recent orders) and which items the customer named (to pick between several orders). | Found in M5: a VIP's general complaint was being tied to their only recent order, adding a wrong high-value signal. |
| D-036 | 2026-09-27 | Near-duplicate merging (FR-3): intake finds *candidates* (same sender, same mentioned orders, inside the window, not a reply in the thread). The merge is confirmed only once the understanding step shows the same intents. Otherwise it is a new case. | Avoids merging "where is it?" with "please cancel it" sent ten minutes later. |
| D-037 | 2026-09-27 | Automated mail is closed at intake from headers and sender alone (Auto-Submitted ≠ no, X-Autoreply, Precedence bulk/junk/list, List-Unsubscribe/List-Id, delivery reports, mailer-daemon/postmaster/noreply senders), with no LLM call. Spam without such headers is left to the LLM. | FR-6 with spam precision 1.0: header rules never fire on real customer mail in the dataset. |
| D-038 | 2026-09-27 | A follow-up that names no order inherits the orders of earlier emails in its case (FR-4). Repeat-contact count = this email + earlier emails in the case or about the same order (router history) + customer contact history, within the window. | FR-4, FR-16. |
| D-039 | 2026-09-27 | `clock.process_at_received_time` (replay mode) evaluates each email as of its `received_at`, as the dataset labels assume. Live runs use the injected clock. | Deterministic dataset replay (NF-2). |
| D-040 | 2026-09-27 | An "understander" can be plugged into the pipeline: the LLM in M6, recorded outputs in replay, or an oracle built from labels. The oracle lets identity, decision and action steps be evaluated without any LLM (EV-4 component evals). | Separates LLM quality from code correctness in evals. |
| D-041 | 2026-09-27 | LLM providers: LM Studio and OpenRouter share an OpenAI-compatible adapter (httpx, `response_format: json_schema`, strict). Anthropic uses the official `anthropic` SDK with structured outputs (`output_config.format`). Provider-wide request fields live on the provider (`extra`), step-specific ones on the step, so switching a step's provider never carries the old provider's fields. `temperature: null` means "don't send" (current Claude models reject sampling parameters). | CF-2, LL-4. Found when an overlay switch carried LM Studio's `reasoning_effort` into an Anthropic request. |
| D-042 | 2026-09-27 | Qwen 3.8 on LM Studio runs with `reasoning_effort: none`. With thinking on, LM Studio returned the JSON in `reasoning_content` with an empty `content`, and it was slower. The adapter still falls back to `reasoning_content` and strips `<think>` and code fences. | Measured in M6 probing. |
| D-043 | 2026-09-27 | Schemas sent to providers are made strict (every property required, `additionalProperties: false`, refs inlined, numeric and length limits removed). Full constraints are enforced afterwards by Pydantic plus extra validation (known intent, ISO language code, non-empty evidence). Invalid output is retried with the reason appended to the user message, up to `retries`; after that → LLMFailure → the case goes to a human (`understanding_failed`). | LL-3: degrade to a human, never guess. |
| D-044 | 2026-09-27 | An intent is **uncertain** if its confidence is below its configured threshold **or its evidence quote is not found in the email**. Uncertain → case routed to a human with the best guess (FR-15). An uncertain `spam_or_auto` is never closed. Order ids from the model are used only if their digits appear in the email. | FR-13, FR-15, spam precision 1.0, protection against hallucinated ids. |
| D-045 | 2026-09-27 | Default judge model is `google/gemma-4-31b` on LM Studio, a different model family from the generator (Qwen), per EV-8. The Anthropic eval overlay uses `claude-opus-5` for understand/summarize/compose and `claude-sonnet-5` for the judge (again a different model from the generator). | EV-8 "separately configured". |
| D-046 | 2026-09-27 | Eval runs record every LLM output to `evals/recordings/<name>.jsonl`, keyed by provider, model, prompt digest and full input. `--mode replay` makes no model calls and reproduces the run exactly. The recordings are committed, so anyone can replay. | EV-1, NF-2. |
| D-047 | 2026-09-27 | Two dev labels corrected after reviewing model disagreements. D154: the Spanish email also asks for an invoice, a second intent (`other`). D074: "was I charged twice?" is a `billing_dispute` as well as a `payment_issue`. Rule: a label changes only when re-reading the email shows the label was wrong, never to match a model. | D-048 | 2026-09-27 | Understand prompt history, all tuned on dev only. **v1**: macro-F1 0.965 (0.979 after D-047); errors were extra intents and anger over-scoring, all in the safe direction. **v2**: asking for a refund is a remedy, not `refund_status`; a chargeback threat is tone, not `billing_dispute`; side remarks are not intents; anger means angry words.
